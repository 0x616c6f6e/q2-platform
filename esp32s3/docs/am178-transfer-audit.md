# AM178 / CO5300 数据传输审查（2026-10-10）

> 后续修复已完成：tx_color 错误回传、日志与实际配置同步、single-transaction 可选后端。
> 下文保留修复前审查记录；最新用法见 [V7 诊断](am178-blue-test.md)。尚无实机通过结论。

## 结论与证据边界

当前现象与像素数据模式有关，传输路径值得优先排查。但代码审查及宿主内存模拟没有发现
把 F0/FF 特判、截断或当作命令的软件逻辑。尚无实际 CS/CLK/D0–D3 波形或屏幕显存读回，
不能宣布已找到根因，不能把 DMA 回调等同于屏幕写入成功，也不能因此排除模组端问题。

检查对象是当前 WSL 源码和本地 ESP-IDF v6.1-rc1，不保证用户板上正运行此源码生成的固件。
未修改 Q2/厂商测试的运行逻辑、当前用户色表、背景、时钟或初始化寄存器。

## 当前两条路径

Q2 独立颜色测试：

```
q2_am178_blue_step: uint32_t 0x00RRGGBB
  -> q2_am178_blue_patch: 填满 uint32_t 矩形，stride=width*4
  -> backend.flush: 按 stride 取像素、软件旋转至物理 368x448
  -> q2_am178_pack_pixel: RGB888 R/G/B 或 RGB565 高字节/低字节
  -> PSRAM shadow frame（已经是最终发送字节序）
  -> 偶数窗口扩展、逐行 memcpy 至内部 DMA tile（10 行上限）
  -> draw_band: esp_lcd_panel_draw_bitmap + 等待 DMA 信号量
  -> OSPTEK 驱动: 加 x_gap=16、发送 CASET/RASET/RAMWR
  -> ESP-IDF esp_lcd SPI IO
  -> SPI master / GDMA / GPIO matrix
  -> CLK/CS/D0-D3 引脚 -> 连接线/转接板 -> CO5300
```

厂商独立颜色测试：

```
颜色常量 -> pack_pixel -> 内部 DMA 缓冲
  -> fill_rect -> 相同 OSPTEK 驱动 -> 相同 ESP-IDF SPI IO -> 同一硬件
```

第二条绕开 Q2、LVGL、旋转和 PSRAM shadow，但不绕开 OSPTEK 驱动及 ESP-IDF。
两边都复现只能缩小共同故障范围，不能直接认定屏幕损坏或排除软件传输。

## 像素表示与长度

RGB888 中 0x00FF00F0 是 C 数值；ESP32 内存中的 uint32_t 字节序本身不用于发送。
代码显式右移提取 R/G/B，最终 DMA 字节为 FF 00 F0；不会直接发送 F0 00 FF 00。
`0x00RRGGBB` 的高 8 位没有发送。没有字符串终止符、透明色或转义处理。

| 数值 | RGB888 字节 | RGB565 字节 |
|---|---|---|
| A00000 | A0 00 00 | A0 00 |
| F00000 | F0 00 00 | F0 00 |
| F80000 | F8 00 00 | F8 00 |
| FF0000 | FF 00 00 | F8 00 |
| 0000F0 | 00 00 F0 | 00 1E |
| 0000F8 | 00 00 F8 | 00 1F |
| 0000FF | 00 00 FF | 00 1F |
| FF00F0 | FF 00 F0 | F8 1E |
| FF00F8 | FF 00 F8 | F8 1F |
| FF00FF | FF 00 FF | F8 1F |

565 与 888 的“F8”不是相同线数据，必须同时记录格式。565 的红/蓝 F8 与 FF 等价。
Q2 编译配置当前选择 RGB888；产品头实际亮度 100%、旋转 90°、448x368。
独立 Kconfig 中的亮度 25/旋转 0 在产品构建中不生效，不可只看 sdkconfig 判断。

RGB888 原生一帧 = 368*448*3 = 494592 字节；565 = 329728 字节。
原生完整 10 行 tile 的 RGB888 长度是 11040 字节，565 是 7360 字节。
窗口实际宽度决定提交长度，缓冲容量不等于实际发送长度。当前每个矩形有显式字节数，
无 strlen 或按颜色决定长度的分支。SPI API 的 length 最终换成字节数*8，单位为 bit。

## DMA 所有权与切片

Q2 的 shadow 在 PSRAM，真正传给 SPI 的 tile 来自 INTERNAL|DMA 内存。
旋转只变坐标，不变颜色；窗口向偶数边界扩展时从 shadow 补邻居，不越界读取调用者像素。
每次 draw_band 等待回调后才允许覆盖 tile，始终至多一个像素块在途。
厂商新测试亦在覆盖缓冲前等待信号量。信号量若先于等待到达，二值信号量会保存通知。

底层 IDF 若需要临时 DMA 内存只会 memcpy；没有对 RGB 值进行解释。
SPI 事务可以在 GDMA 内部拆成描述符，描述符边界不应改变字节内容，也不是额外屏幕命令。
这属于静态设计审查和宿主模拟结果，尚未验证实机 GDMA/引脚输出。

## 实际命令序列

以厂商测试中心 48x48 的第一块 48x10 为例：物理逻辑范围 x=160..207、y=200..209；
加屏幕 X gap 后，GRAM x=176..223。下面是期望的总线顺序，不是实测抓包：

```
CS 拉低
  单线 D0: 02 00 2A 00 00 B0 00 DF
CS 拉高
CS 拉低
  单线 D0: 02 00 2B 00 00 C8 00 D1
CS 拉高
CS 拉低
  单线 D0: 32 00 2C 00
  保持 CS 有效，切换四线
  四线 D0-D3: F0 00 00 重复 480 次（测试 F00000 时）
CS 拉高
```

单次颜色块为 1440 字节。完整 48x48 色块分 10/10/10/10/8 行，共 6912 字节。
每块重新设置窗口并用 2C 开始；不是固定一个大窗口然后错误地多次从窗口起点覆盖。

CO5300 手册第 20–24 页规定 32h 后地址阶段为 24 个单线时钟，之后进入四线像素阶段。
当前 32 位头恰好是 8 位指令+24 位地址，和 12h 的四线地址协议不同。
无需为了使用 32h 像素写入就先发 38h 切换整个接口；混用模式反而会改变头部解释方式。

ESP-IDF 并没有用硬件 command/address 字段发送这个头：它先作为单线 data buffer 轮询发出。
随后为像素排队，设置 SPI_TRANS_MODE_QIO。头部设置 CS_KEEP_ACTIVE，最后的数据事务解除该位。
同一设备 acquire_bus 覆盖这段提交过程。源码意图是 CS 全程保持有效；两事务间可能有停钟间隔，
实际是否存在 CS 毛刺、额外 CLK 或 GPIO 切换异常必须测量，不能从 flags 推断实测波形。

32 位 C 命令 0x32002C00 在小端内存是 00 2C 00 32；IDF 仅对这个命令缓冲反序，
得到 32 00 2C 00。参数宽度为 8 位，不反序参数；颜色缓冲完全不经过该反序函数。
因此不能对 RGB888 颜色再额外执行 RGB565 swap 或整个数组倒序。

## 四线位模式

按手册第 22 页，每个字节分高、低两个 nibble：D3..D0 先承载 bit7..4，再承载 bit3..0。

| 字节 | 第一个时钟 D3..D0 | 第二个时钟 D3..D0 |
|---|---|---|
| A0 | 1010 | 0000 |
| F0 | 1111 | 0000 |
| F8 | 1111 | 1000 |
| FF | 1111 | 1111 |

这是检查数据相关异常的有用波形，不能据此直接宣布 D3 坏了。
特别是 F0、FF 的各个 nibble 全 0 或全 1，纯粹交换 D0-D3 顺序不会改变它们；
单纯的线序交换不足以解释它们失败而 F8 可写。固定高/低、串扰、阈值、模式切换等是不同问题。
FF 在指令阶段有协议意义，不代表颜色数据里的 FF 必须转义；当前代码按像素原样发送是对的。

引脚映射：CLK=4、CS=16、D0=5、D1=6、D2=7、D3=15、RST=17。
检查了 IDF GPIO matrix 初始化：四根线都配置输出通路，D1 不只是输入 MISO。
手册第 107 页要求数据建立/保持各至少 4ns，CS 建立/保持各至少 10ns，
上升/下降时间最大 3.5ns。因此降低 SCLK 能增加周期，却不能证明电平或边沿质量符合要求。
逻辑分析仪适合查位流和 CS/CLK；模拟电平、毛刺及边沿质量需要示波器。

## 已确认的问题及其解释能力

1. **厂商驱动吞掉 tx_color 错误。** `esp_lcd_qspi_amoled.c:280` 调用后直接返回 ESP_OK。
   用实际函数提取构建的宿主桩注入 0x103 错误，确认 draw_bitmap 仍返回 0。
   Q2 外层通常会因没有 DMA 回调而超时，但底层错误原因被丢失。应修复可观测性，
   目前没有证据证明这是特定颜色失败的根因。
2. **DMA 回调不是面板 ACK。** IDF 的回调仅说明主机侧事务结束；DMA 返回队列中的故障可能
   在下一次 get_trans_result 才暴露。即便主机完全无错，也不能证明屏幕正确接收。
3. **Q2 测试说明已落后于用户修改。** 当前 LEVELS=9、STEPS=1*LEVELS，实际仅运行 10MHz；
   baseline 实际为 000000，日志仍写 A0 红底、两档频率、F0/F8/FF/08。
   这是当前磁盘源码状态，不用于否定之前两档频率的实测。
4. **厂商新测试 ISR 返回值在该 SDK 被忽略。** callback 返回 wake，但本地 IDF 不消费返回值；
   可能等待下一个 RTOS tick 才唤醒。Q2 已显式 portYIELD_FROM_ISR。
   这影响速度，不会在正常完成后把 F0/FF 特判丢弃。
5. **原版对照并非完全相同初始化。** 本地 bringup/new test 的 63=FF，Q2=80；
   bringup/new test 先 51=A0 再覆盖 FF，Q2 初始化一次写 FF。两边 58=07。
   独立测试还移除了 Q2 旋转，并使用不同矩形；不能把所有差异都归入“是不是 LVGL”。

## 下一步最有区分度的对照

1. 保持初始化、色值、亮度、频率、矩形一致，修正日志与真实测试设置的对应关系。
2. 在厂商测试工程增加独立直连 SPI 后端：使用硬件 command_bits=8、address_bits=24，
   cmd=32、addr=002C00、仅数据阶段 QIO，用一笔硬件事务完成头与像素。
   它绕开 esp_lcd 的“单线轮询头 + 四线排队数据”两事务切换，不改 LCD 初始化参数。
   这是诊断方案而非已证明的修复；需要另写并验证。
3. 如果仍失败，使用相同协议的小矩形，分别做 DMA 和无 DMA 的对照。
   注意 polling_transmit 只是调用/等待方式，启用 DMA 的 bus 下仍会用 DMA；不能称它为无 DMA。
   无 DMA 测试必须显式禁用 DMA，并保证事务长度在硬件 FIFO 限制内。
4. 在屏幕端抓 CS、CLK、D0-D3，对比 F0/F8/FF 实际位流，优先确认 header 后 1->4 切换、
   CS 是否连续、像素总时钟数、字节顺序。若位流相同而视觉不同，再要求厂家确认模组特有配置。

## single 后端创建时报 INVALID_ARG 的修复

ESP-IDF 6.1 的 SPI master 状态在首次 spi_bus_add_device 时才创建。
先调用 spi_bus_get_max_transaction_len 会在刚初始化的总线上返回 ESP_ERR_INVALID_ARG。
后端现改为先添加设备，再查询传输上限；查询失败时移除刚添加的设备。
主机测试模拟这种延迟初始化行为，并检查失败清理，避免仅靠编译漏掉调用顺序问题。
这解决的是屏幕初始化之前的后端创建错误，颜色显示仍需实物测试。
